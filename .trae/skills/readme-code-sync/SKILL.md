# README 与源码增量同步

把 README/设计文档与**当前**源码保持一致的证据驱动流程。不重写未漂移的内容，
不凭记忆描述代码，不借文档任务顺手改代码。

## 触发场景

- 用户要求在 README/文档中补充某模块的「核心设计、架构取舍、机制说明」
- 代码近期有演化（超时、重试、并发、协议、配置项变更），文档可能已过时
- 用户说「更新文档 / 补齐设计点 / 文档与代码对齐」之意

不适用于：全新文档撰写、代码重构、运行验证类任务。

## 工作流程

### 1. 冻结范围

- 仅修改文档文件；发现代码 bug 或代码↔样例不一致时，在回复中如实报告
  （附 file:line），**不擅自改代码**，除非用户明确授权。
- 不新增用户未要求的 *.md 文件；优先编辑既有 README。

### 2. 证据先行（最关键一步）

1. 先 Read 目标文档中要落点的章节，确定精确插入/替换位置。
2. 再通读相关源码的**当前版本**——本仓库演化快，禁止复用上一轮对话中
   读过的代码记忆。同一模块的所有文件都要读（如 scheduler 改了，ws.ts
   的释放时机可能联动变化）。
3. 为每条准备写入的结论建立证据链：`结论 → 文件:行号`。
   - 数值类（间隔、超时、截断长度、重试次数、端口、默认值）必须逐字来自源码；
   - 配置项以 `config.ts` 实际读取的环境变量名为准，`.env.example` 只是样例；
   - 协议字段只认 `packages/shared/src/protocol.ts`。
4. 扫不到证据的内容不写；用「可能/大概」补齐属于事故。

### 3. 章节级最小替换

- 用 Edit 做最小片段替换，保留所有仍然准确的旧内容；不整篇重写。
- 每个小节遵循统一口径：**机制事实（怎么实现）→ 为什么这样设计 → 取舍/边界**。
- 描述并发/时序机制时，明确指出临界区是否跨 `await`、同步还是异步、
  事件先后顺序，并给出对应代码位置。
- 已知缺陷与竞态窗口要写「诚实清单」：写明触发条件、实际后果、兜底机制，
  以及可选的收敛方向，但不夸大为严重 bug。

### 4. 口径回收（防止同一事实多处冲突）

改完正文后必须联动检查：

- 「架构取舍一览」表格：新设计点是否需要新增行？旧行表述是否已失效？
  表格固定三列：`选择 | 放弃的方案 | 换来什么 / 代价`。
- README 前文（架构图、「三个分离」、概述段）是否与新内容矛盾。
- 全局搜索旧术语/旧数值/旧变量名，确认无残留旧口径。

### 5. 交付回复

- 用中文，按「改了哪几节、每节关键变更、发现的代码↔文档漂移」组织。
- 引用代码用可点击的绝对路径链接加行号，例如：
  [scheduler.ts#L121-L135](file:///Users/daqiao/Documents/workspace/harness-mvp/packages/gateway/src/scheduler.ts#L121-L135)
- README 文件内部的交叉引用用相对路径（如 `packages/gateway/src/ws.ts#L89-L91`）。
- 不附带测试、构建、运行验证类叙述，除非用户明确要求。

## 参考资料

  关键数值位置与口径回收检查清单。每次执行前读取，注意其中的数值表
  仅作索引用，写入文档前仍需回源码复核。

## 反模式（本仓库踩过的坑）

- 凭上一轮读过的源码直接写文档——代码已新增 healthCheck / 双超时等机制。
- 文档任务中顺手做代码重构或变量改名，扩大变更面。
- 只改正文，不回收取舍表与 .env.example 的旧口径。
- 把样例文件（.env.example、注释）当成事实源，与 config.ts 冲突时以样例为准。
- 文档中加入未被要求的验证步骤、运行命令章节。
